## Слайд 1. Цель проекта и основной пользовательский сценарий — около 1 минуты

### Что разместить на слайде

Название проекта: «Медицинская информационная система поликлиники».

Три роли:

- пациент;
- врач;
- администратор.

Основной процесс:

```text
Регистрация → запись на приём → расписание → приём → медицинский итог → история пациента
```

### Текст выступления

«Мой проект — медицинская информационная система для поликлиники. Основная цель — объединить в одном приложении запись пациентов, работу врачей с расписанием и медицинскими итогами, а также административное управление.

В системе есть три основные роли. Пациент выбирает цель обращения, врача, дату и свободное время. Врач видит своё расписание, открывает карточку пациента, завершает приём и заполняет медицинский итог. Администратор управляет пользователями, справочниками, расписанием, филиалами и переносом записей.

Проект развивался вокруг полного сквозного сценария: пациент не просто создаёт строку в базе, а проходит процесс от выбора услуги или цели до сохранения результата приёма».

### Фрагмент кода для показа №5: статусы

**Файл:** `src/main/java/com/example/medicalsystem/model/AppointmentStatus.java`, строки 3–15.

```java
public enum AppointmentStatus {
    pending, confirmed, cancelled, completed, no_show;

    public boolean occupiesSlot() {
        return this == pending || this == confirmed;
    }

    public boolean canTransitionTo(AppointmentStatus next) {
        return switch (this) {
            case pending -> next == confirmed || next == cancelled
                    || next == no_show || next == completed;
            case confirmed -> next == cancelled
                    || next == completed || next == no_show;
            case cancelled, completed, no_show -> false;
        };
    }
}
```

### Что сказать

«Статусы оформлены как отдельная модель. Только `pending` и `confirmed` занимают слот. Финальные состояния нельзя вернуть назад: например, завершённую или отменённую запись нельзя снова подтвердить».

## Слайд 5. Защита от конфликтов на уровне базы — около 50 секунд

### Фрагмент кода для показа №6

**Файл:** `microservices/db/migrations/V2__appointment_slot_constraints.sql`, строки 22–31.

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_active_doctor_appointment_slot
    ON appointments (id_doctor, appointment_date)
    WHERE id_doctor IS NOT NULL
      AND appointment_type = 'DOCTOR_VISIT'
      AND lower(status) NOT IN (
          'отменен', 'отменён',
          'завершен', 'завершён', 'пропущен'
      );

CREATE UNIQUE INDEX IF NOT EXISTS uq_active_patient_appointment_slot
    ON appointments (id_user, appointment_date)
    WHERE lower(status) NOT IN (
        'отменен', 'отменён',
        'завершен', 'завершён', 'пропущен'
    );
```

### Текст выступления

«Проверки есть на уровне Java-сервиса, но критические ограничения дополнительно закреплены в базе. Частичные уникальные индексы запрещают две активные записи врача на один слот и две активные записи пациента на одно время.

Это важно при одновременных запросах. Даже если два пользователя почти одновременно выберут один слот, база остаётся последним уровнем защиты от дублирования.

В проекте миграции хранятся SQL-файлами V1–V7. При этом нужно честно отметить, что в текущем `pom.xml` не обнаружен подключённый Flyway или Liquibase, поэтому автоматическое применение этих миграций при старте нельзя утверждать без отдельной проверки».

### Что показать

Открыть миграцию V2 и выделить два индекса. Не нужно читать SQL целиком — достаточно объяснить, что именно ограничивается.

**Бизнес-сервисы:**

```text
.\mvnw.cmd -Dtest=DoctorPatientsControllerTest,AppointmentServiceTest,AppointmentSlotHoldTest test
```

не прошла этап компиляции тестов. Причина — тест `AppointmentControllerOwnershipTest` вызывает старую сигнатуру метода `showEditForm`, а текущий контроллер требует дополнительный параметр `returnUrl`.

Поэтому на защите нельзя говорить, что текущая рабочая копия полностью проходит все тесты. Корректная формулировка: «В проекте есть тестовое покрытие ключевых сценариев, но текущая незакоммиченная версия требует обновления теста после изменения сигнатуры контроллера».

# Порядок демонстрации в IDE

1. Открыть главную страницу и кратко назвать три роли.
2. Открыть `Pr3p7Application.java` и показать точку входа.
3. Открыть `Appointment.java` и показать сущность записи и связи с пациентом и врачом.
4. Показать форму пациента `patientBookingWizard.html`.
5. Перейти к `AppointmentService.saveBooking` и показать последовательность проверок.
6. Открыть `AppointmentStatus.java` и объяснить состояния записи.
7. Показать миграцию V2 с уникальными индексами.
8. Открыть врачебную карточку и форму медицинского итога.
9. Показать `MedicalRecordController.java` с транзакцией и созданием назначения.
10. Показать `AdminSchedulingController.java` с `requiresReschedule`.
11. Открыть `api-gateway.yml` и объяснить три бизнес-сервиса и инфраструктуру.
12. Завершить тестами и честной оговоркой о текущей ошибке компиляции тестов.

# Короткая версия для 7 минут

Если времени мало, оставить 7 слайдов:

1. Цель и роли — 45 секунд.
2. Стек и слои — 50 секунд.
3. Запись и проверки — 1 минута 30 секунд.
4. Статусы и защита базы — 1 минута.
5. Врач и медицинская карта — 1 минута 20 секунд.
6. Администратор и микросервисы — 1 минута 20 секунд.
7. Тесты, ограничения и вывод — 1 минута.

В сокращённом варианте достаточно показать четыре фрагмента кода: точку входа, `saveBooking`, `MedicalRecordController.save` и `api-gateway.yml`.

# Версия для 10 минут

Если есть 10 минут, добавить короткую демонстрацию:

- пациент выбирает свободный слот;
- система создаёт временный резерв;
- врач открывает карточку пациента;
- врач завершает прошедший приём;
- врач сохраняет медицинский итог и назначение;
- администратор закрывает даты и получает список записей на перенос.

Код не нужно читать построчно. Для каждого фрагмента достаточно объяснить три вещи: какую проблему он решает, где находится бизнес-правило и какой пользовательский сценарий оно защищает.
